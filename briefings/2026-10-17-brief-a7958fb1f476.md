# 全球网络安全简报（AI 专题）— 2026-10-17（GMT+8）

本期主要覆盖东八区过去约 24～48 小时内可核验的公开披露；其中欧盟委员会将 EN 18286:2026 列入官方公报的实施决定于 10 月 12 日通过、NullHub 管理面缺认证于 10 月 14 日进入 NVD，因直接影响高风险 AI 系统合规路径与智能体控制面，放宽至约 72 小时一并纳入。时效均已对照 NVD / VulnCheck、GitHub Security Advisory、EUR-Lex 原文与项目发布说明核对，不重复前几日已写且无新补丁进展的 Archon、Portkey、Roo Code、MCP SDK 资源耗尽等条目。

### 一、今日要点

**[1] LMCache反序列化RCE获正式补丁**
📌 类型：AI基础设施CVE

GitHub Advisory GHSA-w5f2-9q9c-ff4h 于 10 月 16 日正式发布：LMCache 在 multiprocess / distributed 模式下开放未认证 ZeroMQ 传输端口（默认 5555），msgpack 扩展码在参数解码阶段对载荷执行 `pickle.loads`，可达该端口的未认证客户端可在 LMCache 进程权限下远程执行代码；官方容器此前以 root 运行。漏洞 CVE-2026-105192（CVSS 9.8）影响 0.3.9 起至 0.5.6 之前版本，单机默认绑定本机时外网不可达，多节点将传输绑到可路由地址时风险最高。官方确认修复版本为 0.5.6（10 月 14 日发版），并同步收紧示例 Kubernetes 绑定与非 root 镜像默认值。属已确认高危基础设施缺陷，未见在野利用通报；曾暴露传输端口的主机应按潜在失陷处置。

🔗 来源：[GitHub Advisory GHSA-w5f2-9q9c-ff4h](https://github.com/advisories/GHSA-w5f2-9q9c-ff4h) · [NVD CVE-2026-105192](https://nvd.nist.gov/vuln/detail/CVE-2026-105192) · [LMCache v0.5.6 发布说明](https://github.com/LMCache/LMCache/releases/tag/v0.5.6)

**[2] Claude Agent SDK可被注入MCP执行**
📌 类型：AI自身安全

NVD / 官方 Advisory 于 10 月 16 日披露 CVE-2026-96620（CVSS 4.0 约 9.2 Critical）：Claude Agent SDK for Python 在 0.2.121 之前将 `resume` 选项作为独立 argv 传给 Claude CLI，以 `-` 开头的值会被解析为额外命令行标志。攻击者若能控制作为会话 ID 传入的 `resume` 值，可注入 `--mcp-config` 并定义 stdio MCP 服务器，从而在 CLI 启动时执行任意命令，并绕过 SDK 权限控制。官方修复版本为 `claude-agent-sdk` 0.2.121，将 `--resume` / `--session-id` 改为 `=` 连接的单一参数。属已确认研究披露路径，前提是应用把不可信输入当作会话恢复标识；未见在野利用通报。

🔗 来源：[GitHub Advisory GHSA-h4mw-j7qp-8mwm](https://github.com/advisories/GHSA-h4mw-j7qp-8mwm) · [NVD CVE-2026-96620](https://nvd.nist.gov/vuln/detail/CVE-2026-96620) · [修复提交 / v0.2.121](https://github.com/anthropics/claude-agent-sdk-python/releases/tag/v0.2.121)

**[3] LangChat管理面默认可被接管**
📌 类型：AI自身安全

NVD / VulnCheck 于 10 月 16 日收录 CVE-2026-111704（CVSS 约 9.3–9.8 Critical）：开源对话 / AIGC 平台 LangChat 在指定提交（through `2a6285a`）未注册 Sa-Token 全局拦截器，REST 控制器可被未认证远程访问。攻击者可读取 `/api/v1/auth/users` 明文密码、拉取 LLM 提供商 API 密钥、创建超级管理员并改删业务数据。属已确认默认认证缺失类缺陷；公开材料未给出统一修复版本号，暴露实例应立即下线公网访问并轮换全部密钥。未见在野利用通报。

🔗 来源：[NVD CVE-2026-111704](https://nvd.nist.gov/vuln/detail/CVE-2026-111704) · [VulnCheck Advisory](https://www.vulncheck.com/advisories/langchat-through-commit-2a6285a-missing-authentication-on-rest-api-controllers) · [研究者披露](https://hackmd.io/@hieuPenguinnn/langchat-missing-global-auth-credential-exposure)

**[4] NullHub可未认证接管智能体**
📌 类型：AI自身安全

NVD / VulnCheck 于 10 月 14 日披露 CVE-2026-110616（CVSS 3.1 约 8.1 / CVSS 4.0 约 9.2）：NullHub 至 2026.5.29 的 `/api/*` 管理接口因 `auth_token` 默认为空且未被赋值，在非回环监听且请求不含 Authorization / Origin 头时，未认证调用者可控制 agent 实例、改写含提供商凭据的配置，并管理 cron 与 MCP 服务器。属已确认默认配置缺陷，影响面取决于是否将管理面暴露到非本机网络；公开材料未给出正式修复版本。临时缓解为仅本机绑定、强制管理面认证并隔离 MCP 配置变更权限。

🔗 来源：[NVD CVE-2026-110616](https://nvd.nist.gov/vuln/detail/CVE-2026-110616) · [VulnCheck Advisory](https://www.vulncheck.com/advisories/nullhub-through-2026.5.29-missing-authentication-for-api-management-api)

**[5] 欧盟首个AI Act协调标准生效路径明确**
📌 类型：AI治理合规

欧盟委员会实施决定 (EU) 2026/2274（2026 年 10 月 12 日）决定在《官方公报》公布协调标准 EN 18286:2026《Artificial intelligence – Quality management system for EU AI Act regulatory purposes》，以支持《人工智能法案》Regulation (EU) 2024/1689。决定明确：符合已在官方公报引用的协调标准，可就其所覆盖的相应要求获得合规推定；该标准针对高风险 AI 系统提供商的质量管理体系（含上市后监测相关过程）。此为已确认的监管标准化动作，标准本身仍属自愿采用路径，但为企业对照第 17 条 QMS 义务提供了具有法律确定性的技术路线；高风险义务适用时点仍以法案及后续修订为准。

🔗 来源：[Commission Implementing Decision (EU) 2026/2274（EUR-Lex）](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32026D2274) · [欧盟 AI Act 标准化政策页](https://digital-strategy.ec.europa.eu/en/policies/ai-act-standardisation)

**[6] 边缘语音设备可窃取系统提示与密钥**
📌 类型：AI基础设施CVE

NVD / VulnCheck 于 10 月 16 日收录 CVE-2026-111623（CVSS 约 5.6–6.3）：xiaozhi-esp32-server-java 至 6.1.0 的 `/api/device/ota` 可对任意 MAC 签发有效设备 WebSocket 令牌。未认证攻击者可接入受害设备通道，读取私有角色系统提示、写入对话历史、消耗 LLM / STT / TTS 凭据并覆写设备元数据。属已确认边缘 AI 服务端认证绕过；公开材料未给出统一补丁版本。缓解重点为限制 OTA / 设备鉴权接口暴露、校验设备身份绑定并轮换推理与语音服务密钥。

🔗 来源：[NVD CVE-2026-111623](https://nvd.nist.gov/vuln/detail/CVE-2026-111623) · [VulnCheck Advisory](https://www.vulncheck.com/advisories/xiaozhi-esp32-server-java-through-6.1.0-authentication-bypass-via-ota-endpoint-token-issuance)

**[7] 低权限账户可读出LLM提供商密钥**
📌 类型：AI自身安全

NVD / VulnCheck 于 10 月 16 日披露 CVE-2026-111682（CVSS 3.1 6.5 / CVSS 4.0 7.1）：Kafka 运维平台 EFAK 5.0.0–5.1.0 的 `/api/model-config` 缺少管理员门禁，任意 `ROLE_USER` 认证账户即可通过分页或按 ID 查询读取未掩码的 LLM 提供商 API 密钥，进而滥用提供商账户并产生费用。同日另有 CVE-2026-111681 指向用户管理接口缺授权。属已确认授权缺失；公开材料未给出统一修复版本。企业应立即限制模型配置接口仅管理员可访问、轮换已泄露密钥并审计近期推理调用账单。

🔗 来源：[NVD CVE-2026-111682](https://nvd.nist.gov/vuln/detail/CVE-2026-111682) · [VulnCheck Advisory](https://www.vulncheck.com/advisories/efak-5.0.0-through-5.1.0-missing-authorization-via-api-model-config-exposes-api-keys)

### 二、深度速览

#### 【AI 赋能防御】

Red Hat 于 10 月 15 日发布《Open Source Security Signals | Q3 2026》，将智能体时代的漏洞优先级从“按严重级别排队”转向“按攻击路径与可组合性评估”：较低严重度缺陷在代理链式利用下可升格为高影响路径，并援引 IBM X-Force 对前沿模型发现漏洞样本的统计（高危占比与远程可达比例偏高，属厂商/研究样本数据）。对已建设 AI 辅助漏洞运营的团队，本期可落地的是：把 MCP 组件、编排框架与推理依赖纳入同一可达性上下文，优先处置可被代理自动串联的入口，而不是仅按 CVSS 排序。

🔗 来源：[Red Hat Open Source Security Signals Q3 2026](https://www.redhat.com/en/blog/open-source-security-signals-q3-2026)

LMCache 0.5.6 将 pickle 从设备 IPC 描述符路径移除，并默认收紧管理 HTTP 与容器权限，属于推理缓存层的基础硬化：对使用 vLLM 等多机 KV 共享的部署，升级缓存层与限制传输端口，可直接压缩“合法内部协议面”被外网触达后的代码执行窗口。

🔗 来源：[LMCache v0.5.6 发布说明](https://github.com/LMCache/LMCache/releases/tag/v0.5.6) · [GitHub Advisory GHSA-w5f2-9q9c-ff4h](https://github.com/advisories/GHSA-w5f2-9q9c-ff4h)

#### 【AI 系统风险】

本期高影响面继续落在两类机制。其一是“把内部协议当可信通道”：LMCache 多进程传输无认证却反序列化不可信消息；Claude Agent SDK 把会话恢复值拼进 CLI argv，使 `--mcp-config` 成为权限旁路；NullHub 管理 API 默认无令牌却可改 MCP 与凭据。其二是“AI 控制面缺少认证/授权门禁”：LangChat 未挂全局拦截器即可读密钥与建超管；边缘设备 OTA 令牌可被任意 MAC 骗取；运维平台模型配置对普通用户回显明文密钥。共性缓解是：对 Agent / MCP / 推理管理面默认本机或零信任接入、禁止将不可信字符串直接拼入 CLI / 反序列化路径、对密钥类接口强制管理员角色与掩码返回，并在暴露后轮换提供商凭据。

🔗 来源：[Claude Agent SDK Advisory](https://github.com/advisories/GHSA-h4mw-j7qp-8mwm) · [LangChat VulnCheck](https://www.vulncheck.com/advisories/langchat-through-commit-2a6285a-missing-authentication-on-rest-api-controllers) · [NullHub VulnCheck](https://www.vulncheck.com/advisories/nullhub-through-2026.5.29-missing-authentication-for-api-management-api)

#### 【全球治理与标准】

欧盟委员会实施决定 (EU) 2026/2274 将 EN 18286:2026 作为《人工智能法案》支持性协调标准列入官方公报引用清单，使符合该标准的高风险 AI 系统提供商可就其所覆盖要求获得合规推定。此为监管层标准化进展，而非新的独立强制法规文本；企业仍需对照自身是否属于高风险提供商及适用时间表评估。其余 NIST / ISO / OWASP 本日无单独强制更新需单列。

🔗 来源：[EUR-Lex Decision (EU) 2026/2274](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32026D2274)

### 三、今日趋势洞察

推理侧缓存 / Agent SDK / 智能体管理面三类“内部协议”在同日披露中同时暴露未认证反序列化、CLI 参数注入与默认空令牌问题，说明 AI 运行时信任边界仍常被实现成调试接口而非安全边界。与此同时，欧盟以协调标准引用的方式把高风险 AI 的 QMS 要求落到可推定合规的技术文本，使“系统侧修洞”与“组织侧建 QMS 证据链”开始在同一周并行加压。

### 四、企业行动清单

- 盘点所有 LMCache / vLLM 多机 KV 共享节点：确认传输是否绑定可路由地址，并升级至 lmcache 0.5.6 及以上。
- 审计基于 Claude Agent SDK 的应用：禁止将不可信输入传入 `resume` / `session_id`，并将依赖升级至 0.2.121 及以上。
- 对 LangChat、NullHub 及同类 Agent 管理面做公网暴露扫描：未认证可达的立即切断外网并轮换提供商 API 密钥。
- 检查边缘语音 / 设备 OTA 与模型配置接口：校验设备身份绑定，限制普通用户读取明文 LLM 密钥。
- 由合规与产品安全联合对照 EN 18286:2026 / Decision (EU) 2026/2274，盘点高风险 AI 系统清单与 Article 17 QMS 证据缺口。
